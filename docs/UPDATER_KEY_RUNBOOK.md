# Updater Key Runbook — Tauri Updater Signing Key (Channel A)

> ## ⚠️ LOUD WARNING — READ THIS FIRST
>
> **Losing the updater private key — or its password — permanently orphans
> every installed copy of this app.**
>
> The public key is embedded in the shipped binary (`tauri.conf.json` →
> `plugins.updater.pubkey`). The updater will **only** install artefacts
> signed with the matching private key. If that private key is lost, no
> future update can ever verify against the installed base: those installs
> become **unupdatable, reinstall-only**. There is no recovery, no reset,
> and no workaround that preserves the update path.
>
> Treat this key like the deed to the product. Custody below is a
> **release-blocking checklist item** (Master Roadmap §11.4 / §11.8).
> Never commit the private key to git. Never put it in chat, email, a
> document, an issue, or a log. Refer to it by path / secret name only.

Source of truth: Master Roadmap `~/workspace/youtube-windows-agent/MASTER_ROADMAP.md`
§11.3 (code signing), §11.4 (Update Channel A — Tauri updater), §11.5
(Update Channel B — separate backend key), §11.8 (release-day checklist).

---

## 1. What this key is — and what it is not

- **This keypair:** minisign keypair generated by the Tauri signer
  (`tauri signer generate`). It signs Tauri updater artefacts for
  **Channel A (shell + UI)** only. The updater plugin verifies that
  signature against the pubkey embedded in the app before installing
  anything.
- **Not Authenticode:** Windows / SmartScreen verify the Authenticode
  certificate (§11.3); the updater verifies minisign. They are two
  different signatures for two different checks (§11.4). One does not
  substitute for the other.
- **Not the backend key:** Update Channel B (Python backend packages,
  §11.5) uses a **different, separate minisign keypair**, generated later,
  with a different blast radius and independent rotation. **Never reuse
  this updater keypair for Channel B, and never reuse the Channel B key
  for Channel A.** A compromise of one must not be able to forge updates
  for the other.

## 2. Key custody (§11.4 — normative)

The production private key and its password live **only** in these places:

| Copy | Location | Notes |
|---|---|---|
| Primary (signing) | CI secrets: `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | The only place the key is *used*. CI signs updater artefacts with these secrets; no human handles the key during a release. |
| Escrow (offline) | Offline escrow copy in the project password manager | For disaster recovery only. Access must be recoverable by a **second** team member (§11.8 item 5) — a release only one laptop/person can sign is a release-process failure. |
| Public half | `src-tauri/keys/updater-pubkey.txt` in this repo, merged into `tauri.conf.json` → `plugins.updater.pubkey` | Public material. Safe to commit, safe to print. Embedding it is what makes verification possible — and what makes losing the private half fatal. |

Nowhere else. In particular:

- **Never in git** — not in history, not in a “temporary” commit, not in
  an ignored-but-shared folder. This repo ignores `.secrets/` and `*.key`
  (see `.gitignore`, “Secrets — NEVER commit”); verify before every
  commit that touches the repo root (see §6).
- Never on a developer laptop as the *production* copy, never in cloud
  drive / chat / email, never printed in build logs. CI must mask the
  secret values, and signing steps must not echo them.

## 3. The key generated in Round 6 is a DEV key

A keypair was generated locally during Round 6 (Tauri Shell Completion)
to prove the toolchain and wire the updater code:

- Private key file (DEV): `.secrets/tauri-signing.key` in the repo
  working tree — git-ignored, **never staged, never committed**
  (verified with `git check-ignore` + `git status`).
- Public key file: `.secrets/tauri-signing.key.pub`, copied to the
  committable `src-tauri/keys/updater-pubkey.txt`.
- It was generated **passwordless** (`-p ''`) for this pre-release stage
  only, so no password had to transit chat, logs, or this repo.

That is acceptable **only** for development. Before the first public
release, all of the following are mandatory:

1. **Generate the production keypair in CI** (or on a designated,
   controlled machine whose only job in that session is this
   generation), with a **strong password**.
2. Store the production private key **only** as the CI secrets
   `TAURI_SIGNING_PRIVATE_KEY` / `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`,
   and place the offline escrow copy in the project password manager at
   the same time. Confirm a second team member can recover the escrow
   copy (§11.8).
3. **Replace the pubkey** in `tauri.conf.json` (`plugins.updater.pubkey`)
   with the production public key (source of truth for the merge:
   `src-tauri/keys/updater-pubkey.txt` — update that file in the same
   change). Every build shipped publicly must embed the production
   pubkey; a build embedding the DEV pubkey would strand its users when
   the key rotates to production.
4. **Destroy local copies** of the DEV private key (delete
   `.secrets/tauri-signing.key` and any copies/backups) once it is no
   longer needed for local testing, and destroy any local copy of the
   production private key if one was ever created during generation —
   after verifying the CI secrets and the escrow copy both work.
5. Record (in the release ticket, **without** any key material): date,
   who generated the production key, where the escrow copy lives, and
   who verified second-person recoverability.

## 4. If the key (or password) is lost

There is no recovery procedure for the installed base — that is the
point of the warning at the top:

1. Generate a new production keypair per §3 and embed its pubkey in the
   next release build.
2. Accept that **all installs carrying the old pubkey can never update
   to it**. Those users must be reached out-of-band (download page,
   channel/community posts) and must **reinstall manually**.
3. Keep the canonical download page on one domain / URL pattern (§11.3)
   so stranded users have exactly one obvious place to get the new
   build.

Prevention is the whole strategy: CI secrets + password-manager escrow
+ second-person recoverability, verified on every release (§11.8).

## 5. Rotation procedure

Rotate when: the private key or password may have been exposed, a person
with sole escrow access leaves, or on a planned, deliberate schedule —
never casually, because rotation has the same orphaning effect as loss
for any install that misses the bridge.

1. Generate the **new** keypair (production procedure, §3, steps 1–2).
   Do not delete the old CI secrets or escrow yet.
2. Ship a **bridge release**: a normal update **signed with the OLD key**
   whose embedded pubkey is the **NEW** public key. Installs on the old
   key verify this release (old signature ✓), and after installing it
   they trust only the new key.
3. Promote the bridge release through all rollout rings (§11.6) and wait
   until adoption is effectively complete (plus a grace period for
   tray-resident / rarely-opened installs). Installs that never take the
   bridge release are stranded and become reinstall-only — say so in the
   release notes before starting.
4. Sign all subsequent releases with the **new** key only; update the CI
   secrets to the new key/password; move the new escrow copy into the
   password manager and mark the old escrow entry superseded.
5. Only after step 3’s grace period: retire the old CI secrets and the
   old escrow copy. Record the rotation (dates, versions, bridge release
   number — no key material) in the release ticket.

Emergency variant (key confirmed compromised): skip the grace period —
ship the bridge release immediately, rotate CI secrets as soon as the
bridge is published, and treat any artefact signed with the old key
after the compromise time as untrusted. Note that a compromised old key
can also sign a hostile “bridge” — in that case prefer direct user
communication and manual reinstall over trusting the bridge path.

## 6. Handling rules for anyone touching this key

- Generate with the Tauri CLI from the repo root, e.g.
  `npm run tauri signer generate -- -w <path-outside-git-or-in-.secrets/> -p '<password>' --ci`
  (check `npm run tauri signer generate -- --help` — flags change
  between CLI versions). Never paste the private key value into a
  terminal command that will be logged, a chat, or a ticket.
- After any local generation, prove the key is not in git before doing
  anything else:
  - `git check-ignore .secrets/tauri-signing.key` must print the path
    (ignored), and
  - `git status --porcelain` must show **no** entry for `.secrets/`.
- The **public** key is the opposite: it is meant to be published. Its
  committable copy is `src-tauri/keys/updater-pubkey.txt`; the config
  fragment for merging it into `tauri.conf.json` is
  `src-tauri/keys/UPDATER_CONFIG.md`. An empty or mismatched pubkey in
  the shipped config means **every update fails closed, by design**
  (see `src-tauri/src/updater.rs`).
- Passwordless keys are a **pre-release development convenience only**
  (see §3). A production key without a password, or a production
  password stored next to the key, both void the custody model in §2.

## 7. Channel B reminder (do not conflate)

The backend-channel key (§11.5) does not exist yet. When Channel B is
built, generate its keypair **fresh, separately**, store it under
**different** CI secret names and a separate password-manager entry,
and document it in its own runbook section. Reusing the Channel A
keypair “temporarily” is forbidden — temporary reuse has a way of
becoming the shipped design, and it collapses the two blast radii into
one.
